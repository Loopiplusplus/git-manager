# git-manager · 产品构想与技术方案

> 一句话定位：**一个苹果风、只读优先的本地 Git 体检与维护中枢，专为 vibe coding 项目设计，并作为所有 AI 的统一接入层。**

---

## 0. 结论先行

| 维度 | 决策 | 理由 |
|---|---|---|
| 核心定位 | 本地仓库「体检室」+ AI「上下文供给站」 | vibe coding 的痛点是维护，不是写代码 |
| 接入方式 | **中途接入**：只扫描本地 `.git`，零侵入、不碰工作区 | 用户已有大量历史仓库，不能要求重建 |
| 形态 | 优先 **桌面端（Tauri/Electron）**，先做 Web 版验证 | 桌面端才能无摩擦读本地文件系统 |
| 只读/写 | **默认只读**；写操作分三级（L0 只读 / L1 可回滚写 / L2 破坏性写），L1 以上独立隔离 + 确认 | 安全第一，避免 AI 误删 |
| 分支切换 | **可视化切换**（⌘K 面板），但走「Preflight 检查 → 自动快照 → `git switch`（禁 force）→ 校验 → 可回滚」 | 第一个写操作，详见 `02-分支切换与安全模型.md` |
| AI 接入 | 暴露一个 **MCP Server** + 结构化 JSON / Markdown 上下文包 | 让任何 AI（含我）都能调用 |
| 前端风格 | Apple 风：大留白、SF Pro、克制配色、玻璃拟态点缀 | 用户明确要求 |

## 1. 要解决的真正问题

vibe coding 的项目不是「不好用」，而是**难维护**：

1. **状态不透明** —— 我到底改了多少？哪些分支是半成品？
2. **AI 痕迹难追溯** —— 哪些提交是 AI 生成的？AI 在哪些文件反复返工？
3. **债务堆积** —— 临时分支、堆积的 stash、WIP 提交、TODO/FIXME、大文件。
4. **AI 每次都要重新理解仓库** —— 缺少一份标准化的「仓库现状快照」。

所以本系统要回答三个问题：
- **现在健康吗？**（健康度评分 + 问题清单）
- **AI 在哪儿动的手？**（AI 参与度、返工率、提交节奏）
- **接下来该收拾什么？**（可执行的清理建议 + 一键导出上下文给 AI）

**关键设计原则：分层解耦**。前端只跟服务层说话；服务层只调分析层；想换 git 引擎（CLI → libgit2 → isomorphic-git）不影响上层。

## 3. 「中途接入仓库」怎么做

**零侵入接入流程：**
1. 用户选一个本地文件夹（或拖拽）。
2. 向上查找 `.git`（支持 worktree，`.git` 为文件的情形）。
3. 只读探测：`HEAD`、`refs/`、`packed-refs`、`config`、`index`。
4. 建立缓存记录（首次全量、后续增量）。
5. **不修改、不 checkout、不 fetch**（除非用户显式点「刷新远端」）。

**安全边界（红线）：**
- 默认全部只读。
- 写操作按三级模型授权：**L0 只读**（status/log/diff）→ **L1 可回滚写**（commit / 新建分支 / stash / **切换分支**）→ **L2 破坏性写**（`branch -D` / `stash drop` / `reset --hard` / `push --force`）。
- L2 必须逐条列出受影响对象 + 二次确认；L3（如无 dry-run 的 `clean -fdx`）永不自动执行。
- 删除分支优先用 `git branch -d`（-d 而非 -D）。
- **分支切换**用 `git switch` 而非 `git checkout`，永不使用 `--force`；详细流程见 `02-分支切换与安全模型.md`。
- 禁止清单写在**引擎层**（命令白名单），不写在 UI 层——UI 和 AI 都能被绕过。

## 4. 数据模型与扫描能力

| 模块 | 采集内容 | 用途 |
|---|---|---|
| 仓库概览 | 分支数、提交数、贡献者、时间跨度、`.git` 体积 | 仪表盘首屏 |
| 提交健康度 | 频率、粒度（平均改动行/文件数）、大提交告警、WIP 提交（wip/tmp/fixup）、空提交 | 健康度评分 |
| 分支与引用 | 本地/远端分支、stale 分支（90 天无提交）、未合并分支、tag、worktree、stash 堆 | 清理建议 |
| 文件热度 | 改动最频繁文件、大文件（>5MB）、二进制文件、`.gitignore` 覆盖率 | 仓库瘦身 |
| AI 参与度 | commit message 中的 AI 署名 / Co-Authored-By / 生成器指纹、提交时段分布（深夜= vibe 特征） | 差异化核心 |
| 工作区状态 | 未提交改动、未跟踪文件、被忽略文件统计 | 维护面板 |
| 时间线 | commit graph（父子关系、分叉合并） | 可视化图谱 |

**vibe coding 专属指标（建议）：**
- **AI 参与度** = 带 AI 署名/AI 生成特征的提交占比。
- **返工率** = 同一文件在 24h 内被反复修改的次数。
- **半成品比** = WIP 提交 / 总提交。
- **债务信号** = TODO/FIXME 密度、stale 分支数、stash 深度。

## 5. 健康度评分（示例算法）

```
score = 100
 - 8 × (stale 分支数)              # 超过 90 天无提交
 - 6 × (WIP 提交占比 × 10)
 - 5 × (stash 数量 > 5 ? 过量级数 : 0)
 - 4 × (大文件数)
 - 3 × (返工热点文件数)
 - 2 × (TODO/FIXME 每百行 > 阈值)
最终 clamp(0, 100)，并映射等级：
90+ 优秀 / 75+ 良好 / 60+ 需关注 / <60 需清理
```
> 权重可配置，评分规则放进分析层插件，方便迭代。

## 6. AI 接入层（本系统的差异化核心）

把分析能力封装成 **MCP Server**，暴露以下工具：

| MCP 工具 | 说明 |
|---|---|
| `git_overview(repo)` | 返回结构化仓库概览 JSON |
| `git_health_report(repo)` | 健康度评分 + 问题清单 |
| `git_recent_changes(repo, since, author)` | 近期变更摘要 |
| `git_ai_usage(repo)` | AI 参与度与返工热点 |
| `git_suggest_cleanup(repo)` | 可执行的清理建议 |
| `git_context_bundle(repo, format)` | **导出精简上下文包（Markdown/JSON），直接喂给 AI** |

**上下文包（context bundle）是重点**：把仓库现状压缩成一份 1–2k token 的结构化 Markdown，任何 AI 一读就懂这个项目现在什么样，不需要重新扫仓库。

**同时提供 REST/JSON 兜底**：不接 MCP 的 AI 也能通过 `http://127.0.0.1:PORT/api/...` 消费。

## 7. 技术选型

**方案 A（推荐：质感优先）**
- 壳：**Tauri 2**（Rust）；git 引擎：`git2-rs`（libgit2）
- 前端：React + TypeScript + Vite；图表：Visx 或 ECharts（轻量定制）
- 优点：体积 ~10MB、启动快、渲染接近原生、苹果风最好还原
- 代价：Rust 侧有一定开发量

**方案 B（推荐：速度优先）**
- 壳：**Electron**；git 引擎：`simple-git`（调 CLI）或 `isomorphic-git`
- 前端：同上
- 优点：全是 JS，生态成熟、迭代快
- 代价：体积大（~150MB）

**方案 C（最快验证）**
- 先做**本地 Web 版**：Node 起一个 127.0.0.1 服务读本地 git，浏览器访问
- 优点：当天出原型；后续可平移到 A/B

> 建议路径：**先用 C 验证交互与数据模型 → 再用 B 快速做完整版 → 若追求极致质感迁到 A。**

## 10. 风险与注意

- **跨平台路径**：Windows 路径与换行符（CRLF）要专门处理。
- **巨型仓库**：首次全量扫描要流式 + 可中断，避免卡死。
- **缓存一致性**：外部 `git` 操作会改变 `.git`，需要基于 HEAD/mtime 的失效策略。
- **AI 误操作**：写操作必须隔离 + 二次确认，默认只读。
- **署名识别不准**：AI 参与的判断是启发式，UI 上要标明「估算」而非事实。
